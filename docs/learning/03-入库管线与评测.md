# 入库管线与评测

检索的前提是有索引可查，检索的价值要用评测证明。本文讲两件事：语料怎么从 md 文件变成「带双索引的 chunk」，以及三组消融怎么证明双路互补不是白做。前半段是「建索引」，后半段是「证价值」。

> 阅读起点：读过 [00-RAG从零到双路召回](00-RAG从零到双路召回.md)。源码根为 `apps/api/src/rag/` 与 `corpus/`。

## 语料构成与来源

语料是 50 篇电商平台规则与法规：`laws/` 16 篇（消保法、广告法、电商法等）、`rules/` 28 篇（抖音/淘宝/京东/拼多多/快手/微信小店规则）、`helpdocs/` 6 篇（平台 FAQ）。每篇带 frontmatter，记录 `source`（抓取 URL）与 `collected_at`（采集日期）。

合规红线是「只收公开可浏览页面、每篇必有出处」：法规来自 gov.cn 等官方公开文本，平台规则优先官方公开页、反爬时用公开转载全文并双重标注出处。这批语料决定了评测结论的边界——它只覆盖电商规则/法规这一个域，不能外推到其它领域。

## 入库管线：从 md 到双索引 chunk

入库分五步，每一步都有明确的边界：

```text
语料 md
  → 解析 parse：读出有序文本块（段落 + 表格）
  → 分块 chunk：600 字/块、重叠 100、表格原子
  → 分词 tokenize + 向量化 embed：每块算 tsvector 输入 + 1024 维向量
  → 事务入库 ingest：单事务写 chunk + 更新文档状态
  → 状态机：UPLOADED → QUEUED → PARSING → INDEXED（或 FAILED / OCR_NEEDED）
```

### 解析与质量探测

正式路径支持 PDF（`pdf-parse`）与 DOCX（`mammoth`），解析器输出统一的 `TextBlock[]`（文本、页码、标题路径、是否表格）。demo 与评测的语料是 md，直接当纯文本块走分块器，跳过解析器。

质量探测是防脏数据：CJK 可打印率低于 60% 或全文不足 200 字，说明是扫描件或空文件，置为 `OCR_NEEDED` 终态等人工处理，不硬解。

### 分块：600±100、重叠 100、表格原子

分块器把文本切成目标 600 字符的块，相邻块重叠 100 字符：

```ts
const TARGET = 600   // 目标块字符数
const OVERLAP = 100  // 相邻块重叠字符数
```

600 是召回粒度与上下文成本的平衡：bge-m3 8k 窗口下，600 字约 300–400 token，一个块既能承载完整语义，又不至于把无关内容塞进生成。重叠 100 是为了不让一句话被硬切在块边界上——关键信息恰好在 600 处断开时，前后两块都能看到它。

表格是特殊块：整表原子落块，不并入段落缓冲、也不拆。表格被拆开就失去语义，所以宁可让它单独成块。

### 分词 + 向量化：32 条一批

每块算两个索引值：分词结果（给 tsvector）和向量（给 HNSW）。向量化按 32 条一批调用 embedding，减少 HTTP 往返：

```text
chunks[0..31]  → 一次 embedMany → 32 个 1024 维向量
chunks[32..63] → 一次 embedMany → ...
```

### 事务入库：幂等 + 租户过滤

写库走 raw SQL 的 `INSERT ... ON CONFLICT DO UPDATE`，幂等键是 `(docId, seq)`：

```sql
INSERT INTO knowledge_chunks ("docId", seq, content, embedding, tsv, ...)
VALUES (...)
ON CONFLICT ("docId", seq) DO UPDATE SET content = EXCLUDED.content, ...
```

同一文档重跑不产生重复 chunk，这对评测复现很重要——语料入库可以缓存，重跑不重新烧 embedding。文档状态 `INDEXED` 与 chunk 在同一事务里更新，保证前端轮询到 `INDEXED` 时一定带着完整 chunk。

chunk 表本身没有 `enterpriseId` 列，租户隔离靠检索时 `JOIN knowledge_docs` 用 `enterpriseId` 过滤：

```sql
FROM knowledge_chunks c
JOIN knowledge_docs d ON d.id = c."docId"
WHERE d."enterpriseId" = ${enterpriseId}
```

这是 raw SQL 口的隔离点：chunk 的归属通过它所属的文档间接确定，所以两条检索路的 SQL 都必须带这个 JOIN，否则跨租户泄漏。隔离复验见 `apps/api/src/demo/isolation.ts`。

### 状态机与异步 worker

上传不阻塞入库。文档先落 `UPLOADED`，入队后由 BullMQ worker 异步走完解析→分块→向量化→入库，状态逐级推进。终态只有两个：`INDEXED`（成功）和 `OCR_NEEDED`（需人工）。`FAILED` 不是终态，向量化失败会抛错让 BullMQ 重试（attempts=3），重试时跳过已是终态的文档。

## RRF 融合的边界情况

融合的纯函数 `rrfFuse` 在 [00 的「六 双路 + RRF 融合」](00-RAG从零到双路召回.md) 讲过，这里补三个边界：

**单路退化**：`channel='lexical'` 时向量路不参与，每块的 `rrfScore` 只由词法名次决定，退化为 `1/(60+rank)`，等价于「按词法名次排序」。所以消融时三组用的是同一套融合逻辑，只是参与的路径不同。

**降级冷却**：网关的 HealthTracker 连续 3 次失败把 embedding 通道打入 60 秒冷却，冷却期 `embeddingHealthy()` 返回 false。`channel='auto'` 据此跳过向量路；若向量路仍被尝试但失败，`Promise.allSettled` 把它收口成空路，词法路照常返回。

**全部命中与全部落空**：两路都命中某块时它拿两份名次分；某路没命中就只拿一份。多跳题（跨文档对比）里 auto 的 Recall@10 到 100%，正是「两路互补命中」的直接体现。

## 三组消融评测

评测要回答三个质疑：「双路是不是白做」「词法是不是摆设」「向量是不是噱头」。方法是对同一批题分别跑三组通道，比召回与排序。

### 题目与指标

golden 集 100 题：单跳事实 40、多跳对比 30、数值计算 20、拒答陷阱 10。指标定义：

| 指标 | 定义 |
| --- | --- |
| Recall@5 / @10 | 前 5 / 前 10 个 chunk 命中任一 gold 关键词的题占比 |
| MRR@10 | 首个命中 chunk 名次的倒数均值，衡量「对的那个排多靠前」 |
| 拒答正确率 | 陷阱题检索是否返回不含答案的片段 |

gold 用**关键词命中近似**而不是 chunk 级人工标注：每题标 2–4 个特征词组，chunk 含任一即算召回。这是个人项目量级的诚实近似，其偏差方向是**偏乐观（高估真实 chunk 级召回）**——chunk 含关键词未必含完整答案；反之关键词写法不一致时也有少量低估。

### 结果

| 组 | Recall@5 | Recall@10 | MRR@10 | P50 延迟 | P95 延迟 |
| --- | --- | --- | --- | --- | --- |
| lexical | 93.3% | 95.6% | 0.910 | 7ms | 9ms |
| vector | 92.2% | 97.8% | 0.887 | 112ms | 372ms |
| auto（双路） | **97.8%** | **98.9%** | 0.904 | 111ms | 471ms |

分题型看 Recall@10：多跳题 vector/auto 都到 100%（语义跨文档召回），数值题 lexical/auto 到 100%（数字精确匹配），单跳题三者都在 97.5% 附近、差异不显著。

三个质疑各自被反驳：词法不是摆设（数值题 MRR=1.000，数字精确匹配的强项），向量不是噱头（多跳题 Recall@10=100%），双路不是白做（auto 的 Recall@5=97.8%，同时高于两单路的 93.3% / 92.2%）。

### 成本与复现

embedding 走 bge-m3 免费，一次全量评测查询向量约 5544 token、成本 0 元。评测入口 `pnpm eval:rag` 支持 `EVAL_SMOKE=1` 先跑 5 题冒烟再全量，报告头部写死 commit、语料采集日期、运行日期。检索层是确定性的，重跑同题集数字一致，差异只可能来自 embedding 上游的延迟抖动。

## 规模与局限

- 100 题、单一语料域（电商规则/法规）是个人项目量级，不是生产 benchmark，结论不可外推。
- 关键词近似 gold 偏乐观，报告数字不能对外宣称是真实 chunk 级召回。
- 两组数字差异小于 2pp 时（如单跳题的 vector 97.5% vs auto 97.5%）如实视为「不显著」，不粉饰。
- 拒答在检索层是退化的（陷阱题无关键词可命中），真正的拒答在生成层，靠 LLM 判断并输出「无法回答」类表述，由端到端补测。
