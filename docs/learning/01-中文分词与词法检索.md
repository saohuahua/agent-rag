# 中文分词与词法检索

词法路解决「精确匹配」：数字、条款编号、专有术语不能被语义近似吞掉。它的难点全在中文没有词边界，分词责任必须上移到应用层，再交给 Postgres 全文检索。本文拆开讲三件事：jieba 怎么切、tsquery 怎么拼、GIN 索引和 ts_rank 怎么配合。

> 阅读起点：读过 [00-RAG从零到双路召回](00-RAG从零到双路召回.md) 的「三 中文为什么必须自己分词」「四 词法路」。源码根为 `apps/api/src/rag/`。

## 为什么 Postgres 默认解析器切不了中文

Postgres 全文检索的 `to_tsvector` 依赖一个解析器把文本切成词。英文靠空格和标点就能切，中文没有空格，默认解析器把连续汉字当**一个**词：

```text
to_tsvector('simple', '七天无理由退货')
-- '七天无理由退货':1    ← 整串一个 lexeme

to_tsvector('simple', '七天 无 理由')
-- '七天':1 '无':2 '理由':3   ← 手动空格隔开才是三个 lexeme
```

这意味着语料里写「七天无理由退货」，用户查「七天无理由」就匹配不上——查询词和语料词不一致，召回直接漏掉。解决方向是：**在应用层把中文先切成词，再用空格拼接交给 Postgres 的 `simple` 配置**（`simple` 只做小写，不再切词，避免二次切词破坏 jieba 的结果）。

## jieba 怎么切

项目用 `@node-rs/jieba`，是 jieba 分词器的 Rust 绑定，在任务 0 依赖白名单内。加载默认词典：

```ts
import { Jieba } from '@node-rs/jieba'
import { dict } from '@node-rs/jieba/dict'

let jieba: Jieba | null = null
function getJieba(): Jieba {
  if (!jieba) jieba = Jieba.withDict(dict)  // 默认词典约 5MB 进程内只载一次
  return jieba
}
```

分词用 `cutForSearch` 而不是 `cut`：

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| `cut` 精确模式 | 长词优先，切得粗 | 需要精确词边界时 |
| `cutForSearch` 搜索引擎模式 | 长词进一步切细，兼顾长词与短词 | 检索召回，宁可切细也不漏 |

搜索引擎模式对「七天无理由退货」会切出「七天」「无」「理由」「退货」等细粒度词，这样查询「无理由」或「退货」都能命中，而精确模式可能只给「七天无理由」「退货」两个大块。

`tokenize` 的完整流程是切词 → 清洗 → 去重：

```ts
export function tokenize(text: string): string[] {
  const seen = new Set<string>()
  const out: string[] = []
  for (const raw of getJieba().cutForSearch(text, true)) {
    const t = cleanToken(raw)
    if (t === null) continue
    if (seen.has(t)) continue
    seen.add(t)
    out.push(t)
  }
  return out
}
```

## tsquery 特殊字符为什么必须清洗

`to_tsquery` 的表达式里，`& | ! ( ) : ' " * ^ \` 是运算符或引号。如果 jieba 切出的 token 里带着这些字符（比如英文编号 `3C*`、或带引号的词），会被解析成运算符，轻则语法错误、重则改变查询语义。所以清洗掉：

```ts
const TSQUERY_SPECIALS = /[&|!():'"*^\\]/g

export function cleanToken(raw: string): string | null {
  const t = raw.replace(TSQUERY_SPECIALS, '').trim()
  if (!t) return null
  if (/^\s*$/.test(t)) return null
  return t
}
```

保留字母数字与连字符（`7天` `3C` 这类中文术语里的数字、英文词组里的连字符都要保留），只剔除会干扰语法的符号。

## 拼 OR 表达式：宽容匹配再排序

切完词拼成查询表达式。用 OR 而不是 AND：

```ts
export function toTsquery(tokens: string[]): string {
  return tokens.join(' | ')
}
// ['七天','无','理由','退货','起算'] → '七天 | 无 | 理由 | 退货 | 起算'
```

AND 要求所有词都命中，中文分词可能有偏差（某个词切错了），AND 会直接空结果。OR 宽容匹配，只要命中任意几个词就能进候选，再靠 `ts_rank` 把「命中更多词、词更相关」的排前面。召回优先、排序兜底。

## tsvector / tsquery / ts_rank 三件套

| 部件 | 方向 | 说明 |
| --- | --- | --- |
| `tsvector` | 入库 | 存「词 + 位置」，`to_tsvector('simple', 分词空格串)` 生成 |
| `tsquery` | 查询 | 查询表达式，`@@` 判断 tsvector 是否匹配 |
| `ts_rank` | 排序 | 相关度打分，词频与位置综合 |

入库时生成 tsvector：

```ts
export function toTsvectorInput(tokens: string[]): string {
  return tokens.join(' ')
}
// ['七天','无','理由'] → '七天 无 理由'
// 入库 SQL：to_tsvector('simple', ${tsvInput})
```

查询时：

```sql
SELECT ... FROM knowledge_chunks c
JOIN knowledge_docs d ON d.id = c."docId"
WHERE d."enterpriseId" = ${enterpriseId}
  AND c.tsv @@ to_tsquery('simple', ${orExpr})
ORDER BY ts_rank(c.tsv, to_tsquery('simple', ${orExpr})) DESC
LIMIT ${limit}
```

两个要点：`@@` 是全文匹配运算符；`ts_rank` 调用两遍（WHERE 和 ORDER BY 各一次），一次过滤一次排序。

## GIN 索引与验证

`tsvector` 列建 GIN 索引加速 `@@` 匹配。GIN 是倒排索引，把「每个词出现在哪些行」存成索引，适合「包含某词」的查询。

数据量少时 Postgres 的规划器可能选顺序扫描而不是走 GIN（小表全扫更快），这不代表索引失效。要验证 GIN 生效，关掉顺序扫描强制走索引：

```sql
SET enable_seqscan = off;
EXPLAIN (COSTS OFF)
SELECT id FROM knowledge_chunks WHERE tsv @@ to_tsquery('simple','七天 | 退货');
-- 应出现 Bitmap Index Scan on knowledge_chunks_tsv_idx
```

## ts_rank 不是 BM25

诚实标注：`ts_rank` 不是完整 BM25。它计算词频和词位置权重，但没有 BM25 的文档长度归一化与 IDF 那套完整公式，也没有 BM25 可调的两个参数。本项目能接受它，原因是融合层只用名次、不用分数绝对值——`ts_rank` 只要保证「同一查询下更相关的 chunk 分数更高」即可，分数本身的大小和跨查询可比性都不重要。若未来要上真 BM25，词法路这一层可以整体替换成外部检索引擎，融合层不受影响。

## 一条查询在词法路的完整路径

```text
「七天无理由退货从哪天起算」
  → jieba cutForSearch → ['七天','无','理由','退货','从','哪天','起算']
  → cleanToken 清洗 → 同上（无特殊符）
  → toTsquery → '七天 | 无 | 理由 | 退货 | 从 | 哪天 | 起算'
  → tsv @@ to_tsquery('simple', ...)
  → ts_rank 降序 → 词法名次
```

词法路强在「精确」：问 `168小时` 命中的一定是含 `168小时` 的块，问 `退一赔十` 不会漂到 `退一赔三`。它的弱项是改写问法——「买错了能退吗」里没有「退货」「七天」这些词，就召回不到。这个盲区由向量路补齐，见 [02-向量检索与HNSW索引](02-向量检索与HNSW索引.md)。
