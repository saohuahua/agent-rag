# 30-01 · RAG 评测设计（J 任务执行）

> 评测是这个项目区别于「套壳 demo」的灵魂证据。**方法论迁移自作废的财报 RAG 方案**（见 99-归档），规模按个人项目诚实标注。

## 1. 测试集

来源：`corpus/golden/rag-eval.jsonl`（F 任务产出，≥40 题）。四类分布：

| 题型 | 数量 | 例 |
|---|---|---|
| 单跳事实 | 15 | 「七天无理由退货的时限从哪天起算？」 |
| 多跳对比 | 8 | 「直播带货与短视频挂车的违规扣分规则有何不同？」 |
| 数值计算 | 4 | 「预售定金不超过商品价格百分之几？」 |
| 拒答陷阱 | 8 | 「抖音的商家保证金是多少？」（语料若无 → 正确行为=拒答） |

标注口径：`goldKeywords`（2-4 个特征词组，chunk 含任一即算该题召回）——**chunk 级 gold 太重，关键词命中是个人项目量级的诚实近似**，文档如实写。

## 2. 消融矩阵（三组）

| 组 | 配置 | 证明什么 |
|---|---|---|
| L-lex | `channel:'lexical'` 只有词法路 | 基线之一 |
| L-vec | `channel:'vector'` 只有向量路 | 基线之二 |
| L-hybrid | `channel:'auto'` 双路+RRF | **双路互补的价值**（预期：≥两单路最优；多跳/术语题分项差异最大） |

评测入口：`pnpm eval:rag`（Nest `createApplicationContext` 直调 RetrievalService，不起 HTTP）。逐题跑三组，输出 markdown 报告到 `docs/08-阶段总结/评测报告-RAG.md`。

## 3. 指标

| 指标 | 定义 | 说明 |
|---|---|---|
| Recall@5 / @10 | gold 关键词命中任一 chunk 的题占比 | 检索质量主指标 |
| MRR@10 | 首个命中 chunk 名次的倒数均值 | 排序质量 |
| 拒答正确率（陷阱题） | 检索无命中时是否返回空/低分（生成层拒答在 J 的端到端里补测） | 分题型报告 |
| P95 延迟 | 检索链路耗时 | 分组报告 |
| 每查询成本 | embedding 调用 token 计 | 从 usage_records 汇总 |

**诚实条款**：报告必须含「规模与局限」一节（40 题/关键词近似 gold/单一语料域）；两组数字差异 <2pp 时如实写「不显著」，不粉饰。

## 4. 复现

- 报告头部写死：commit hash + 语料版本（corpus/ 的采集日期）+ 运行日期；
- `pnpm eval:rag` 幂等（重跑同题集差异只来自模型输出——检索层确定性，应完全一致）；
- 评测 embedding 查询走真 API（不缓存查询向量，语料入库可缓存）。

## 5. 端到端补测（J 任务）

- 生成层拒答：陷阱题走完整问答（runtime），断言回答含「无法回答/资料未涉及」类表述（LLM-judge 打分，judge prompt 入库版本化）；
- 引用溯源：答案引用的 chunk 可点开原文（人工抽 10 题）。

## 自测题

1. 为什么用关键词命中近似 gold 而不是标注 chunk id？这个近似的偏差方向是什么？
2. 三组消融各自回答什么质疑？（「双路是不是白做」「BM25 是不是摆设」「向量是不是噱头」）
