# 40-01 · 实施总控：任务分解与并行模型

> 本文定义**并行无阻塞**的执行架构：任务 0 串行先行 → A-H/E/F/G 全并行 → J/K 收尾。prompts/ 目录的每个 prompt 对应一个任务。

## 1. 任务依赖图

```
                ┌────────── 并行区（互不阻塞 可任意多开）──────────┐
                │  A 网关      B RAG        C Runtime   D 多租户   │
任务 0 基座 ───>│  E 前端      F 语料采集    G mock工单  H 技能    │
（必须先完成）   └───────────────────────┬────────────────────────┘
                                        │ 全部完成后
                                 J 集成评测种子 ──(可与 K 并行)── K 交付部署
```

- **任务 0 是唯一的串行前置**：建 monorepo/全量 schema/迁移/依赖装齐/契约桩/共享文件。约半天工作量。
- 并行区任务**目录互斥**（见 §2），编译期靠契约桩互相可见，运行期在 J 才真正连通。
- J 必须等 A B C D E H（F 语料也强烈建议先行——B 的真实验收与 J 的评测都要语料；G 要在 J 前完成供 RPA 联动）。K 只依赖任务 0 的构建产物结构，可与 J 并行。

## 2. 目录所有权表（并行纪律的根）

| 任务 | 独占目录/文件 | 严禁触碰 |
|---|---|---|
| A | `apps/api/src/gateway/**` | 其余一切共享文件 |
| B | `apps/api/src/rag/**` | 同上（raw SQL 收口自己写） |
| C | `apps/api/src/runtime/**` | 同上 |
| D | `apps/api/src/tenant/**` + 产出 prisma 扩展补丁说明 | prisma.service 实际修改留给用户 |
| E | `apps/web/**` + shared 的 E 区块追加 | api 目录 |
| F | `corpus/**` | 一切代码目录 |
| G | `apps/mock-rpa/**` | 根 workspace（任务 0 已登记包） |
| H | `apps/api/src/skills/**` + shared 的 H 区块 | runtime（toolbox 是 C 的） |
| J | `scripts/**`、`prisma/seed.ts`（demo 种子）、`apps/api/src/demo/**`（剧本） | 各模块内部实现（发现问题报 issue 不直改） |
| K | `deploy/**`、`.github/**`、各 app `Dockerfile`、`docker-compose.prod.yml`、README | 模块源码 |

**共享文件总清单（只有任务 0 与用户能改）**：`pnpm-workspace.yaml`、根 `package.json`、`docker-compose.yml`、`.env.example`、`apps/api/package.json`、`apps/api/prisma/schema.prisma`、`apps/api/src/app.module.ts`、`apps/api/src/main.ts`、`apps/api/src/config/**`、`apps/api/src/prisma/prisma.service.ts`、`apps/api/src/common/**`（任务 0 建后冻结）、`packages/shared/src/index.ts` 的既有区块（只允许各任务在**自己的区块注释**下追加）。

**通用纪律**（每个 prompt 里都会重复）：
1. 只写自己的目录；import 别的模块可以（契约桩保证编译），改别的模块的文件不行；
2. 不 `pnpm add`（依赖全在任务 0 装齐；缺了在报告里申请）；
3. 不 commit/push——完成即写总结报告，用户审后统一提交；
4. 遵守 [10-骨架/03 代码规范](../10-工程骨架/03-代码规范.md)（自查清单过一遍）；
5. 发现契约/文档缺陷：写进报告的「契约变更提案」小节，不擅自改。

## 4. J（集成）任务范围定义

1. **接线**：把各模块真实现连通（预期问题都在这一步暴露：契约误解/DI 缺失/时序问题）；
2. **demo 种子**：`prisma/seed.ts` 扩展（好物严选企业：部门树/成员/订阅电商套装 v1/6 员工/授权/示例订单数据供 readonly_sql）；
3. **剧本**：`pnpm demo:scenario` 跑完整业务剧本（上传知识→提问→售后工单→handover 扫雷→handover 周报），输出逐步日志与断言；
4. **评测**：`pnpm eval:rag` 三组消融跑批出报告（30-评测/01）；
5. **降级演练**：禁 embedding route→纯词法仍出结果留证；
6. **并发演练**：锁竞争脚本留证；
7. **文档回填**：写 `docs/08-阶段总结/集成报告.md`（含全部真实数字）；遇到模块 bug 列「返工清单」交用户派发。

## 5. 推荐执行顺序（用户操作手册）

1. 先跑 **任务 0**（单会话，完成前不开并行）；
2. 任务 0 验收过 → 开 3-5 个并行会话：建议首批 **A + B + F + G**（F/G 无代码依赖最快出活；A 是最多任务的依赖底座；B 独立性最强）；
3. 第二批补 **C + D + H + E**（A 完成后 C/H 更顺——但靠桩也可同时开，看并行度承受力）；
4. 全部完成 → 用户统一 commit → 跑 **J**（+ 可同时开 **K**）；
5. J 出报告 → 返工清单处理 → 用户走 K 的上线手册（可选上线）→ 进入面试资产阶段（/project-guide 等）。
