# 20-06 · 模块规格：技能执行器（H 任务）

> 三类异构能力统一入口的落地。五段式压缩为：职责与原理 → 八个技能规格 → 执行器实现 → 测试与验收。

## 1. 职责与原理

- **SkillDef**（zod schema+描述）是技能的「协议」——runtime 的 toolbox 拿它构建 AI SDK `tool()`；LLM 看到的就是 description+inputSchema；
- **SkillExecutorRegistry.execute** 是统一执行入口，内部按 Skill.type 分发到三种执行器：
  - `BUILTIN_FUNCTION`：进程内函数（查库/规则引擎/SQL）；
  - `HTTP_RPA`：fetch 外部系统（mock 工单系统），超时+重试+进度事件；
  - `EXTERNAL_AGENT`：以 OpenAI 兼容协议调用外部 agent 端点，注入任务+会话摘要上下文；
- 事件回传：`skillCtx.emit(type, payload)`（函数注入，见 10-骨架/04 §5）；
- 计量：BUILTIN 不计量（无外部成本）；RPA/EXTERNAL 按次记成本（调用量/延迟）。

## 2. 八个技能规格（inputSchema 要点）

| key | type | inputSchema 核心 | 输出 | 讲点 |
|---|---|---|---|---|
| `kb_search` | BUILTIN | `{query: string, topK?: number}` | hits 摘要数组（content 截断+来源） | 直调 RetrievalService（configJson 注入 datasetId 限定范围） |
| `compliance_check` | BUILTIN | `{title: string, category: string, description?: string}` | `{violations: [{word, rule, severity}], passed: boolean}` | 禁限售词表+类目规则**确定性引擎**（正则/词表 不走 LLM）——LLM 调度+规则执行 混合范式 |
| `batch_scan` | HTTP_RPA | `{productIds: string[]}` | 扫描报告（每商品风险级） | fetch `POST mock-rpa:3002/scan`（10s 超时 重试 2 次指数退避；分批进度 SKILL_PROGRESS） |
| `ticket_classify` | BUILTIN | `{ticketText: string}` | `{type, urgency, policyRef}` | 轻分类：调 gateway.chat（cheap 别名）结构化输出（zod 解析 失败重试 1 次） |
| `operate_ticket` | HTTP_RPA | `{ticketId, action: 'refund'|'reject'|'escalate', note?}` | 工单新状态 | fetch `POST mock-rpa:3002/tickets/:id/operate`；**riskLevel=2 写操作** 事件必记 |
| `run_readonly_sql` | BUILTIN | `{question: string, sql: string}` | 查询结果（≤50 行） | **安全边界**：只读角色连接+表白名单（orders/products/refunds 三张种子表）+ `SELECT` 单语句校验+LIMIT 强制注入；不满足即拒 |
| `consult_creative_agent` | EXTERNAL_AGENT | `{brief: string}` | 创意方案文本 | 经 gateway 以 `strong-chat` 别名起一个**独立小 agent**（单轮 system=创意角色 prompt），注入会话摘要上下文——「外部 agent」的最小真实形态 |
| `conversation.handover` | BUILTIN | （runtime 内置 C 任务实现 不在 H） | — | 见 20-规格/03 §4.4 |

## 3. 执行器实现规格

```
skills/
├─ skill-executor.ts          // 契约实现：registry + 按 type 分发
├─ defs/                      // 八个 SkillDef（zod schema+description 中文注释设计意图）
├─ executors/
│  ├─ builtin/
│  │  ├─ kb-search.ts
│  │  ├─ compliance.ts        // 词表放 corpus/compliance/words.json（F 任务产词表 H 读）
│  │  ├─ ticket-classify.ts
│  │  └─ readonly-sql.ts
│  ├─ http-rpa.ts             // 通用 RPA 执行器：configJson.endpoint + 超时重试进度
│  └─ external-agent.ts
└─ errors.ts                  // SkillInputError SkillTimeoutError RpaError
```

**HTTP_RPA 通用执行器**要点（每个坑都有注释）：
- AbortController 10s 超时；
- 失败重试 2 次（指数退避 1s/4s），仅 5xx/网络错重试，4xx 不重试；
- 每次尝试 `emit('SKILL_PROGRESS', {attempt, phase})`；
- 计量：meter.record({kind:'RPA', costCny:0, latencyMs})——成本记 0 但调用量/延迟真实（未来接付费 RPA 时改这里）；
- mock-rpa 地址从 env `MOCK_RPA_URL` 读（默认 http://localhost:3002）。

**readonly-sql 安全边界**（注释必须写全）：
1 连接串用独立只读账号（compose 里加 `POSTGRES_READONLY`?——简化：同库 `SET default_transaction_read_only = on` 会话级）；
2 正则校验单条 `SELECT`（禁分号多语句/注释/DML 关键词）；
3 表名白名单数组；
4 无 LIMIT 自动包一层 `SELECT * FROM (...) t LIMIT 50`。

## 4. 测试与验收

- 每个 skill 至少：合法输入成功、非法输入抛 SkillInputError（zod 失败细节透出给 LLM 以便自我纠正）；
- RPA：mock-rpa 500 两次→第三次成功（重试序正确）；超时中断；
- readonly-sql：`DROP`/多语句/白名单外表全部被拒（这组测试是面试讲安全边界的证据）；
- 验收：六员工剧本中每类技能各有一次成功调用（ExecutionEvent+UsageRecord 双证）。
