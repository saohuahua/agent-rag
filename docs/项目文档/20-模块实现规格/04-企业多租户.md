# 20-04 · 模块规格：企业多租户（M4 · D 任务）

> 五段式：业务问题 → 原理 → 选型对比 → 实现规格 → 面试深挖区。

## 1. 业务问题

平台服务多家企业：A 公司的知识库绝不能被 B 公司搜到（数据泄露=产品事故）；岗位模板要审核后才可上架（prompt 草稿不能直接服务客户）；订阅要锁版本（行为不能半夜被改）。需要：租户隔离、权限体系、不可变版本与审计。

## 2. 原理

- **行级隔离**：所有租户表带 `enterpriseId`，查询强制注入过滤。载体= **AsyncLocalStorage**（Node 的请求级存储，类比 React Context 的服务器版）+ **Prisma Client Extension**（`$extends({ query: {...} })` 拦截所有模型的读写注入条件）；
- **RBAC**：OWNER（企业主，可管理订阅/授权/成员）/ ADMIN（审核模板、管理部门）/ MEMBER（使用会话）；
- **不可变版本**：模板与包 PUBLISHED 后不可改（新行为=新版本行）；订阅锁定版本快照——语义同 npm 的 version pinning；
- **审计**：所有关键状态变更写 AuditLog（before/after JSON）。

## 3. 选型对比

| 决策 | 选 | 没选 | 一句话 |
|---|---|---|---|
| 隔离方案 | 应用层行过滤+ALS | Postgres RLS | driver adapter 连接池下 `SET app.tenant` 会话管理复杂 ORM+raw 双轨更易漏；用「收口+测试矩阵」兜住（讲得出取舍） |
| | | 独立 schema/库每租户 | 隔离最彻底但个人项目成本不成比例；共享库+行过滤是中台主流 |
| Prisma 挂钩 | Client Extension | $use 中间件 | $use 是弃用方向 Extension 是官方正路 |
| 版本 | 不可变版本行 | 单表 version 字段 | 审计/回滚/diff 全靠快照 |

## 4. 实现规格

### 4.1 文件清单（D 任务独占 `apps/api/src/tenant/`）

```
tenant/
├─ tenant.module.ts                // @Global()：EnterpriseContextService/AuthModule
├─ enterprise-context.service.ts   // 契约实现 run/current/require（ALS）
├─ prisma-tenant.extension.ts      // 租户过滤扩展（★共享文件例外 见 10-骨架/04 §6）
├─ auth/ (controller+service)      // 注册/登录/JWT cookie/logout
├─ member.guard.ts                 // JWT→Member→ALS enter（每次请求注入上下文）
├─ role.guard.ts                   // @Roles(ADMIN) 装饰器配套
├─ enterprise.controller.ts        // 企业信息/邀请
├─ invitation.service.ts          // token 邀请（48h 过期 一次性）
├─ department.service.ts          // 物化路径树 CRUD
├─ template/ (controller+service)  // 模板状态机+技能/KB 绑定+审核
├─ package/ (controller+service)   // 包/版本/发布
├─ subscription.service.ts        // 订阅（锁版本）→ provision 员工 → 升级
├─ grant.service.ts               // EmployeeGrant 授权解析
└─ audit.service.ts               // AuditLog 统一写入
```

### 4.2 认证与上下文流

```
POST /auth/register {email, password, enterpriseName}
  → 事务：User + Enterprise(slug 随机) + Member(OWNER) + Department(根 path='/<id>/')
POST /auth/login → bcrypt 校验 → JWT(HttpOnly cookie, 24h)
每个请求：member.guard 解 JWT → 查 Member(活跃) → ALS enter({enterpriseId, memberId, role})
worker/脚本：显式 enterpriseContext.run(ctx, fn)
```

### 4.3 租户过滤扩展（prisma-tenant.extension.ts）

- 拦截 `findMany/findFirst/findUnique/update/delete/count/aggregate`：租户模型清单（硬编码数组，含 12 张租户表）注入 `where.enterpriseId`（`findUnique` 重写为 `findFirst`）；
- create 注入 `data.enterpriseId`；
- **raw SQL 不经扩展**→ 全部收口到各模块的 TenantScopedRepository（B 的 chunk.repository 即一例）+ 每条 raw 一个隔离测试；
- 挂载：D 产出对 `prisma.service.ts` 的 3 行补丁说明（`this.$extends(tenantExtension)`），用户手动应用（唯一共享文件例外）。

### 4.4 模板状态机与审核

```
DRAFT → (submit) → PENDING_REVIEW → (publish by ADMIN) → PUBLISHED   [终态 不可变]
                          └→ (reject, reviewNote) → REJECTED → 可再 submit（同版本行回 PENDING？）
                                                    —— 设计决策：REJECTED 行可编辑后重新 submit（未发布过 可变）
PUBLISHED → (archive) → ARCHIVED
新行为 = 新版本行（version+1 从旧版复制起步）
```

包状态机同款（PackageVersion 复用 TemplateStatus 枚举）。

### 4.5 订阅与 provision

```
POST /enterprises/:id/subscriptions {packageId}
  1 读该包「当前已发布最大版本」v*
  2 事务：Subscription(lockedPackageVersion=v*) + 按 PackageItem 清单 provision
     SiliconEmployee(每模板一条 templateSlug+templateVersion 快照) + AuditLog(SUBSCRIBE)
  3 默认授权：ENTERPRISE scope grant
POST /subscriptions/:id/upgrade
  1 新已发布版本 vN；diff = 对比 v* 与 vN 的 PackageItem 清单
  2 AuditLog(UPGRADE before/after=diff) → 显式确认参数 confirm=true 才执行
  3 更新 lockedPackageVersion + 更新（或重建）SiliconEmployee 快照
```

### 4.6 授权解析（grant.service.ts）

```
canUse(member, employee) =
  存在 ACTIVE grant 且：
    scopeType=ENTERPRISE（同企业） ∨
    scopeType=DEPARTMENT 且 member.department.path LIKE grant.department.path||'%' ∨
    scopeType=MEMBER 且 scopeId=member.id
  ∧ Subscription ACTIVE ∧ employee ACTIVE
```

### 4.7 HTTP API 汇总

auth：register/login/logout/me ｜ enterprise：get/patch(budget 限 OWNER)/invitations ｜ invitation：accept(token) ｜ department：CRUD+tree ｜ template：draft/submit/publish/reject/list/bindings ｜ package：create/version/publish ｜ subscription：create/list/upgrade ｜ grant：create/revoke/list ｜ audit：list(ADMIN)

### 4.8 测试清单（本模块的验收核心=隔离测试套件）

- **隔离矩阵**：租户 A 建数据（企业/部门/数据集/文档/会话/员工/授权各一）→ 租户 B 上下文查全部模型 → 断言 0 行/404；
- **raw SQL 口**：B 的 chunk 检索用 B 租户数据跑一次同款断言（D 写这条测试但放 B 的目录？——放 D 目录 mock 数据直查 repository 属跨目录……**改为**：D 的隔离套件覆盖自己模块的每条 raw；B/J 各自补自己 raw 的隔离测试——写进各任务验收）；
- 状态机：PUBLISHED 不可 UPDATE（尝试→报错）；REJECTED 可改再 submit
- 订阅锁定：发包 v2 后老订阅仍 v1；升级走 confirm+AuditLog
- 授权三层命中/未命中各一；部门子树（孙部门成员可用）
- JWT 过期/无效 401；非本企业 member 403

### 4.9 验收

- 两租户全流程并发操作互不可见（自动化套件全绿）
- 审核上架→订阅（锁 v1）→发 v2→老订阅不动→confirm 升级→AuditLog 有 before/after（演示脚本留证）

## 5. 面试深挖区

- 「为什么不用 RLS？」→ 见 §3；补：如果做 SaaS 卖给高危行业会重新评估 RLS（DB 层强制比应用层纪律硬），个人项目选工程简洁+测试矩阵
- 「ALS 是什么？」→ Node 的异步上下文追踪（AsyncLocalStorage）：同一请求内任意 await 边界都能拿到进入时存的上下文——服务器版 React Context；性能开销极小（native hooks）
- 「物化路径 vs 邻接表 vs 闭包表？」→ 路径=读多写少最优（一个 LIKE 查子树）；部门树改名不改结构（path 用 id 不用名）正好规避了路径的更新弱点
- 「版本锁定的意义？」→ 可审计（谁在何时用哪版）、可回滚、可复现（bug 报告带版本号）；类比 npm lockfile 的企业版
