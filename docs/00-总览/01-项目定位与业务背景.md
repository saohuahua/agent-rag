# 00-01 · 项目定位与业务背景

> 本篇讲**业务逻辑**：这个平台是什么、给谁用、解决什么问题。读完你应该能不看任何技术词，向一个外行讲清楚这个项目。

## 1. 一句话定位

**一个让电商企业「雇佣」AI 数字员工的平台**：企业注册后，订阅岗位包（比如「电商运营套装」），平台自动给企业生成几个硅基员工（规则答疑客服、上架审核员、售后处理员……），员工接入企业知识库、掌握技能（查知识库/操作系统/请外援），在同一个会话里按需接力干活，每一步花多少钱平台都记着账。

对标行业语境（2025-2026）：钉钉 AI 助理、飞书 AI、字节 Coze、Dify 这类「企业 AI 平台」；「数字员工/硅基员工」是行业热词（来也科技自称智能体数字员工平台；周鸿祎 2026 预测「硅基数字员工纳入用工体系」；市场规模口径 2025 年 212 亿 → 2026 年 449 亿）。我们的差异点：**个人开源、可复现、全链路量化**。

## 2. 复刻声明（必读）

本项目**复刻**了一段公开流传的他人简历项目（企业 AI 中台/硅基员工平台）的**技术内核**——原项目五大模块（Agent Runtime、知识库 RAG、多租户、Token 网关、工程交付）逐个真实实现。差异与红线：

| 项 | 原项目 | 本项目 |
|---|---|---|
| 身份 | 公司实习项目 | **个人开源项目**（GitHub + demo） |
| 业务数字 | 100+ 数字员工、服务 10+ 企业、63 个模型 | 只写真实数字（接入 N 个模型、内置 6 个数字员工、demo 地址） |
| 模型接入 | sub2api（订阅转 API，有 ToS 风险） | 自写 OpenAI 兼容网关 + SiliconFlow/DeepSeek 官方 API |
| 部署 | 公司生产环境 | 本地 Docker Compose + 上线操作手册（自行执行） |

**禁止**在任何简历/面试表述中把它包装成实习经历或使用原项目的业务数字。

## 3. 业务场景：一家电商公司的一天

想象一家 20 人的淘宝/抖音店铺运营公司「好物严选」：

- **客服**每天回答几百遍「7 天无理由退货怎么算」——答案全在平台规则文档里，但文档有几百篇，没人读得完；
- **运营**上架新品前要检查标题有没有违禁词、类目对不对——靠人肉翻禁限售目录，漏一次就扣分；
- **售后**处理退货工单：先查政策判断能不能退，再去工单系统点一遍操作——纯体力活；
- **老板**想知道这周哪个品类退货最多——等分析师拉数据，一等一天。

「好物严选」在我们平台上：

1. **注册企业** → 邀请员工进部门 → 订阅「电商运营套装 v3」（**版本锁定**：下周套装升到 v4，不主动升级就一直用 v3，不会半夜被改行为）；
2. 平台**自动生成 6 个硅基员工**并按部门授权（客服部门的成员才能用售后处理员）；
3. 客服把平台规则 PDF **上传进企业知识库**（异步解析入库，不阻塞）；
4. 员工们开始与数字员工**会话**：问规则、审商品、处理工单、出周报——**一个会话里多个数字员工接力**（售后处理完工单，转给扫描员检查同店铺风险，再转给周报员汇总）；
5. 财务月底在**成本报表**看到每个部门、每个会话花了多少钱。

## 4. 为什么每个设计都对应一个业务痛点

| 设计 | 业务痛点 |
|---|---|
| 知识库 RAG（双路召回+降级） | 几百篇规则文档人记不住；语义问法千奇百怪（「退货政策」vs「买错了能退吗」）；embedding 服务偶尔挂了，客服不能因此停摆 |
| 数字员工=岗位模板+版本锁定 | 老板要的是「岗位」不是「聊天机器人」；行为变更必须可控（v3→v4 显式升级） |
| 审核上架流程 | 企业不希望随便一个草稿 prompt 就上线服务客户 |
| 同会话多员工接管 | 售后问题经常牵连违规检查和数据汇总，用户不想开三个窗口重述背景 |
| 算力统一计量 | 老板按部门核算成本；预算超了自动熔断，不会月底收到天价账单 |
| 三类异构能力统一入口 | 技能（查库）、RPA（操作工单系统）、外部 Agent（请外部专家）——用户视角都只是「员工会干活」 |

## 5. 六个数字员工（demo 内容）

| 岗位 | 名字 | 干什么 | 用什么能力 |
|---|---|---|---|
| 规则答疑客服 | 小规 | 平台规则/售后政策问答 | 知识库（注入+工具双模式） |
| 上架审核员 | 上架侠 | 商品信息合规校验，出结构化审核单 | 禁限售词规则引擎+知识库 |
| 违规扫描员 | 扫雷 | 批量扫描店铺商品风险 | RPA 批量调用检查接口 |
| 售后工单处理员 | 售后侠 | 工单分类→查政策→操作系统 | 分类技能+RPA 操作 mock 工单系统 |
| 数据周报分析员 | 周报姬 | 会话数据→周报 | 只读受限 SQL |
| 活动策划助理 | 点子 | 活动创意+合规初筛 | 外部创意 Agent+知识库 |

**接管演示剧本**（一条会话走完）：售后侠处理退货工单 → `handover` 扫雷检查该店铺 → `handover` 周报姬出周报。三个 slot 按序接管、共享上下文、epoch 递增全程可见。

## 6. 原理速览：五个模块解决五类问题（详细规格见 20-模块实现规格/）

```
用户 ──会话──> [M3 Agent Runtime]  ←会话锁/按序接管/工具调用/流式
                 │ 调用
                 ├──[M1 Token 网关]   ←多模型统一入口/计量计费/降级
                 ├──[M2 知识库 RAG]   ←解析入库/双路召回/RRF/降级
                 └──[技能执行器]      ←BUILTIN / HTTP_RPA / EXTERNAL_AGENT
[M4 企业多租户]   ←企业/部门/角色/订阅版本锁定/授权/审计（横切所有模块）
[M5 工程交付]     ←Docker/Caddy/CI/蓝绿（横切）
```
